# Venice-native scoped keys for a contract-wallet vault

Research date: 2026-09-09. Scope: public documentation, Venice's official `veniceai/skills` repo, one live **unauthenticated, free** `GET /api/v1/api_keys/generate_web3_key` (no credential, no key created, no spend), and the existing local docs/evidence. **Nothing here is live funded evidence.** Every "documented" verdict below still needs the bounded live test at the end before any code relies on it.

## Summary verdict

| Capability | Verdict | Basis |
|---|---|---|
| (a) Enforceable spend limit on a key (DIEM/USD) | **Documented, unproven live** | `consumptionLimit.{diem,usd}` + `limitPeriod` `EPOCH|MONTH|LIFETIME` on both `POST /api_keys` and `POST /api_keys/generate_web3_key`. Enforcement granularity (pre-check vs. overshoot by one request) is undocumented. |
| (b) Expiry | **Documented, unproven live** | `expiresAt` on create/web3/update; `keyExpiration` echoed by `/api_keys/rate_limits`. |
| (c) Reliable revocation | **Documented as immediate; in-flight/caching semantics undocumented** | `DELETE /api_keys?id=` needs an ADMIN key. Skills repo: "Revocation is immediate." No TTL, no in-flight statement. |
| (d) Key draws from the vault's DIEM, not USD | **Documented at account level; no key-level DIEM-only switch** | Order is DIEM → bundled credits → USD, account-wide. Only defensive options: keep the account's USD balance at zero, and set `consumptionLimit.usd: 0` (schema allows 0; whether 0 means "block USD" or "no cap" is unproven). |
| Contract wallet (ERC-1271) accepted by `generate_web3_key` | **Unproven, contradicted by wording, circumstantially plausible** | Docs say "signed with the wallet's private key" (EOA framing); no `chainId`/`type` field unlike SIWX. But the error table lists "Could not verify wallet signature: RPC call to verify the signature failed", i.e. verification touches Base RPC, which is how universal (ERC-1271/6492) verifiers work. Inference-path SIWX explicitly advertises `eip1271`; the key-minting path does not. |
| Admin key obtainable by the vault itself | **Documented, unproven live** | `POST /api_keys/generate_web3_key` accepts `apiKeyType: ADMIN` (the docs example is `ADMIN`). Security consequence: any vault signature over a Venice JWT could mint a permanent ADMIN key — the vault's signature policy must gate that message form separately. |

Net: the "vault issues its own scoped keys, gateway leaves the inference path" design is **fully documented for EOAs**; the single unproven link for a contract wallet is whether `POST /api_keys/generate_web3_key` verifies via ERC-1271. Everything downstream (limits, expiry, delete, DIEM-first) is EOA/contract-agnostic once a key exists.

## Answers to the six questions

1. **GET/POST `generate_web3_key`.** Live GET (unauthenticated) returned `{"data":{"token":"<JWT>"},"success":true}`; the JWT header is `{"alg":"ES256"}`, payload `{"iss":"urn:venice:issuer","aud":"urn:generate_web3_key:audience","iat":…,"exp":iat+900}` (15 min). The wallet signs the **raw token string** with `personal_sign` (EIP-191), so an ERC-1271 vault would be asked to validate `hash = keccak256("\x19Ethereum Signed Message:\n" + len + token)`. The POST body is `address, signature, token, apiKeyType (INFERENCE|ADMIN), consumptionLimit{usd,diem,vcu(deprecated)}, limitPeriod, modelPrivacy, description, expiresAt`, no auth header. `address` must hold non-zero sVVV (RPC read). Verification method (ecrecover vs. ERC-1271) is **not stated**; see verdict table.
2. **`POST /api_keys`.** Yes: INFERENCE keys with `consumptionLimit` + `limitPeriod` + `expiresAt`. Requires an **ADMIN** key ("You need an ADMIN key (or parent session)"; INFERENCE keys get `401` on `POST/PATCH/DELETE /api_keys`). For a wallet-owned account the admin key comes from `POST /api_keys/generate_web3_key` with `apiKeyType: ADMIN`, or from the web dashboard after SIWE login.
3. **Revocation.** `DELETE /api_keys?id=<uuid>` → `{"success":true}`; "Revocation is immediate" (skills repo). No documented auth cache TTL, no statement about in-flight or streaming requests. (Unrelated caches: usage-analytics 10 min; `Idempotency-Key` replays 24 h.)
4. **Balance order.** Account-level: `DIEM` → `BUNDLED_CREDITS` → `USD` (VCU deprecated). `GET /billing/balance` reports `consumptionCurrency` and `diemEpochAllocation`; `GET /api_keys/rate_limits` reports per-key `balances.DIEM/USD` and `accessPermitted`. No key-level "DIEM only" flag exists. `402 INSUFFICIENT_BALANCE` when DIEM is exhausted and no USD/bundled credits cover it.
5. **SIWX per-session limits.** None. Limits are per key (Bearer) or per wallet rate limits (x402). Skills repo: "No per-session spending limits are documented — only per-key consumption limits for Bearer auth."
6. **Bootstrap.** "No Venice account required" for the Web3 key; the key is "tied to the staking wallet" and a later dashboard SIWE login "finds the existing user record", so the POST itself appears to create the user record keyed by wallet address. Preconditions: non-zero sVVV at `address`; ≥0.1 **staked DIEM** for DIEM to be spendable. Whether a web3-minted account has DIEM attached without a browser SIWE login is unproven (the funding table marks DIEM "Autonomous? Yes"). A third-party search result mentions a "DIEM Staking Balance Refresh" endpoint (cached staking balance); it was not found on the fetched changelog page or docs index, so treat as unverified.

## Open questions only a live funded test can answer

1. Does `POST /api_keys/generate_web3_key` accept an ERC-1271 signature from a Base contract wallet (error `Wallet signature does not match` vs. `Could not verify wallet signature` vs. success)? Is ERC-6492 (pre-deploy) accepted?
2. Does the user record created by a web3 mint automatically expose the vault's staked DIEM (`/billing/balance.consumptionCurrency == "DIEM"`) without a browser SIWE login? Is the staking balance cached, and for how long?
3. Is `consumptionLimit.diem` enforced before the request (hard cap) or after (overshoot by one request's cost)? What error is returned at the cap?
4. Does `consumptionLimit.usd: 0` block USD fallback, or is 0 treated as "no cap"?
5. Does a deleted key fail the very next request, and what happens to an in-flight stream?
6. Does an ADMIN key minted via web3 keep working after the vault rotates its inference signer (it is account-scoped, so presumably yes) — i.e. is DELETE the only revocation lever?
7. Does `modelPrivacy` or key type restrict access to any model the gateway needs?

## Bounded live acceptance procedure (max $0.01 per inference request; no real credential reused)

Required inputs: canary vault (ERC-1271, Base) holding ≥1 sVVV (mint requirement) and ≥0.1 staked DIEM (spend requirement); the vault's temporary bootstrap signer; a Base RPC; cheapest XS-tier text model from `GET /models` (record the id and price); `max_tokens: 5`. Expected DIEM cost per request: < $0.001 at XS pricing; hard cap `consumptionLimit: {diem: 0.01, usd: 0}`, `limitPeriod: LIFETIME`, `expiresAt` = now + 2 h. Do **not** fund the account with USD or USDC at any point.

1. Record `sVVV.balanceOf(vault)`, `DIEM.stakedInfos(vault)`, and block number. Abort if sVVV == 0 or staked DIEM < 0.1.
2. `GET /api_keys/generate_web3_key`; save token `iat/exp` (redact signature). Compute the EIP-191 hash of the raw token; verify offline that `vault.isValidSignature(hash, sig)` returns `0x1626ba7e` via `eth_call`. Abort if not: the vault policy must first be extended to a dedicated, gated "Venice web3-key JWT" message form, never a generic digest.
3. `POST /api_keys/generate_web3_key` with `address = vault`, `apiKeyType: INFERENCE`, the caps above, `description: "canary-<date>"`. Save HTTP status, exact error string, `data.id`, `last6Chars` (never the secret beyond the test host). Result classifies Q1: success → ERC-1271 accepted; `Wallet signature does not match` → ecrecover-only; `Could not verify wallet signature` → retry once after 30 s, then treat as inconclusive.
4. With the new key: `GET /api_keys/rate_limits` (save `accessPermitted`, `balances.DIEM`, `keyExpiration`) and note whether `/billing/balance` is rejected (INFERENCE) — if you need it, mint one ADMIN key the same way with `expiresAt` = now + 1 h and delete it at the end.
5. One `POST /chat/completions` (`max_tokens: 5`, `stream: false`). Save `x-request-id`/`id`, `usage`, response headers `x-ratelimit-*`, `X-Balance-Remaining`, and `GET /api_keys/rate_limits.balances.DIEM` before/after. Pass only if DIEM decreased, USD did not appear, and `consumptionCurrency == "DIEM"`.
6. Cap test: `PATCH /api_keys` (ADMIN) to `consumptionLimit.diem` = observed spend + 0.0001, then send one more request. Expect a 4xx cap error (record exact code/body). Never raise caps beyond 0.01.
7. Revocation test: start one streaming request, then `DELETE /api_keys?id=` mid-stream; immediately send a second request with the deleted key. Record delete timestamp, the fate of the stream, and the second request's status (expect 401).
8. Delete every canary key (INFERENCE and any ADMIN); confirm via `GET /api_keys` (ADMIN) that none remain, then delete the ADMIN key last and confirm it returns 401 afterward. Record onchain balances again; they must be unchanged.

Evidence to save (redacted): key ids and last-6, request ids, all timestamps (UTC), balances before/after each step, exact error strings, chain block numbers, and the `isValidSignature` eth_call result. Abort conditions: any USD/USDC balance appears on the account; any request cost > $0.01; a cap that does not trigger by step 6; a deleted key that still authenticates after 60 s; any onchain sVVV/DIEM position change; any prompt to sign a message outside the permitted forms.
